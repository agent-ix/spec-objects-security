# SR-007: Risk & complexity review of the issue #13 semantic module contract

## Summary

Scored FR-002..FR-006, NFR-001 and IT-002 on technical risk and volatility
against the landed implementation rather than against the prose, and against
the reference migration `agent-ix/spec-objects-business#4` and its
`spec/reviews/4-semantic-data-schemas/risk-complexity.md` (SR-006). Three
claims were measured here rather than reasoned about. First, the shipped
`schemas/` directory holds 47 files while `semantic.exports` and the manifest's
`data_schema` entries name 23: building a validator registry from the 23
exported files alone and validating a minimal `secret` record raises
`Unresolvable: .../0.2.0/IdentityField.json` before any rule runs. Second, the
`unevaluatedProperties: {not: {}}` seal is defeated by the very technique
FR-006 uses to carry its refusals: a `Draft202012Validator` over a schema whose
`allOf` branch names a key absent from the top-level `properties` accepts that
key (`True`), and the same schema with the branch removed refuses it
(`False`). Third, `.github/workflows/ci.yml` is `workflow_dispatch` only and
its `publish-to-pypi` job carries no `needs:` on the `ci` job, while that `ci`
job delegates to the shared `lib-ci` workflow, which runs `pytest` without
`make dev-quire` and without `npm ci`.

The set is materially riskier than the ten-model business module it copies,
and not only by count. The business module carried ten sealed models with one
`@extension("allOf", …)` predicate class; this one carries 23 object types, 12
open marker models, ten closed vocabularies and two support records, with up to
three extra predicates per model and a second guard reaching into
`operations[].params[]`. Every security refusal FR-006 claims — no embedded
material, no defaulted parameter, no identity field on an audit declaration —
lives in raw `@extension` JSON that the TypeSpec compiler does not type-check,
whose `$ref` strings the generator silently redirects to the semantic-core base
when it does not recognise them, and which no automated gate ever runs.

## Verdict

Plannable, with two findings to disposition before tasking: FND-260 (the only
dispatchable workflow publishes in a job that does not depend on a test job
that is red by construction) and FND-261 (the shipped bundle is not
self-resolving for any consumer that follows the manifest). Both are
disposition-or-ticket decisions, not code changes this review may make. The
remaining findings are plannable as slices, added evidence, and named
follow-on tickets. Counts: 4 high, 11 medium, 4 low.

## Top hazards

1. FND-260 — the publish path is not gated by the test suite, and the test suite is the only thing enforcing FR-006. A dispatch of `ci.yml` publishes the wheel from a job that does not wait for the job that would have failed.
2. FND-261 — 24 of 47 shipped schemas and all of semantic-core are named by no manifest key; a consumer that materializes `semantic.exports` gets 23 schemas and an `Unresolvable` on the first record. Measured, not inferred.
3. FND-262 with FND-264 — every FR-006 refusal rides in unchecked raw JSON on the one top-level key the emitter also uses, and the same construct can unseal a forbidden key. Neither has a test that would notice.
4. FND-263 — ~35 declared keys and eight item rules that `agent-ix/quoin#335` explicitly does not claim; whichever way that mapping lands, reconciling it costs a bump that rewrites all 47 files.
5. FND-266 — the engine under test is installed unpinned, unverified, over plain HTTP, outside the lock, into a security module's test environment.

## Mitigation order

1. Disposition FND-260 and FND-261 with the architect. Both are decisions (gate the publish or state why it is ungated; ship the support and grammar schemas or state that resolution is the consumer's problem), not code this review may write.
2. Add the two cheap detectors that would make FND-262, FND-264 and FND-265 visible: assert each emitted schema's `allOf` branch count against its model's declaration, and sweep every forbidden key of all 23 types against its schema.
3. Pin the Quire wheel exactly, record it in `toolchain.json`, and file the HTTP/`--trusted-host` question against `agent-ix/quire-rs#392` (FND-266).
4. Get this module's keys named in `agent-ix/quoin#335` before the next version bump, so FND-263 and FND-269 are settled while a bump is already being paid for.
5. Close the generator's unknown-name fallback (FND-275) and give IT-002 a control case (FND-274).
